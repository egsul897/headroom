# Phase 3F.1.1 — Residual Safety Failure Forensic Adjudication: Final Report

**Verdict: `PHASE_3F_1_1_RESIDUAL_FORENSIC_GATE_PASSED`**

This is a forensic gate, not a safety gate: it does not require dangerous omissions to reach zero. It requires that the residual failure be understood well enough, with case-level evidence, to make an informed decision about what comes next. That bar is met — and the answer this forensic work found is more specific, more actionable, and more surprising than "routing and materiality still need more tuning."

**The headline finding: roughly 79% of the 89 residual dangerous cases trace to one generalizable, pre-existing Phase 2A structural-parsing defect that neither Phase 3F.1's four workstreams touched nor could have touched — a duplicate structural-node-identity collision affecting 546 of 3,469 distinct node keys in the frozen, permanent Phase 3F structural index.** This is not a Phase 3E router or materiality problem. It sits one full layer upstream, in the shared substrate every later phase depends on — exactly the failure mode Architecture Invariants #18 named and warned could recur. Independent evidence (§20 below) shows this same defect simultaneously defeats Phase 2B discovery and Phase 3E's independent audit in 75% of the cases where both missed the same provision — the two systems failing together for the same underlying reason, not by coincidence.

A second, independently-adjudicated finding: the scoring-methodology fix Phase 3F.1's own report disclosed (union-matching descendants into an exact chapeau match) is itself imperfect — a manual, source-level adversarial audit of the 26 cases it "resolved" found roughly 14-16 are **false credits**: the scorer picked a real but topically unrelated descendant unit, not genuine coverage of what the ground-truth unit actually describes. This is disclosed as a residual scoring defect, not fixed here (production and scoring code are frozen for this phase).

## 21-25: The dominant root cause — a Phase 2A structural-index defect

21. **Primary discovery**: `stage1-all-nodes.json` (the permanent, sealed Phase 3F structural-parsing output, never modified since) contains **546 duplicate structural node keys out of 3,469 distinct keys** (680 excess node instances) across the 4-document DSGR package. `buildStructuralIndex` (`lib/contract-model/compiler/structural-index.ts`, unmodified, read-only-inspected in this phase) populates its `byKey` node-identity map via `byKey.set(n.nodeKey, n)` while iterating nodes sorted by `charStart` ascending — for any duplicated key, only the **last** (highest-`charStart`) physical instance survives; every earlier instance's own `charStart`/`charEnd`/`heading` is silently discarded from every nodeKey-keyed lookup (`getNode`, `getNodeByRef`, `getParent`, and — critically — `getNodeText`'s own boundary computation).

22. **Concretely demonstrated, not just counted.** `doc-a::6.04`'s nodeKey collides across **4 physically distinct document locations**: a Table-of-Contents entry (`charStart` 4,474, correctly headed "Investments, Loans, Advances..."), a stray match inside unrelated definitional text (28,737), the real operative section header (455,225, correctly headed), and a garbled parenthetical cross-reference fragment inside a *different* section's own text (463,451, heading literally `"), except:"`). The last of these four "wins" the node-identity map. Its own recorded `charStart` (463,451) is **greater than** several of the (incorrectly merged) children's own `charStart` values (as low as 29,892) — because `childrenByParentKey` (a *separate* map, populated by unconditional pushes rather than last-writer-wins) merges every duplicate instance's children into one shared list regardless of which physical instance they structurally belong to. The resulting `OWN`-text boundary computation (`charStart` to nearest child `charStart`) collapses to an empty range. The real section's own operative prohibition text becomes unreachable by nodeKey from that point on, even though it is present, well-formed, and correctly parsed as its own node elsewhere in the very same node array.

23. **A second, related but distinct gap: incomplete lettered-subsection detection.** Of the 58 STILL_DANGEROUS cases classified `R17_STRUCTURAL_PARSER_EFFECT`, 58 have **no structural node at all** for their exact sectionRef (not merely a corrupted one) — e.g. `6.01(c)`, `6.01(g)`, `6.01(h)`, `6.01(m)`, `6.01(p)`, `6.01(q)` never became their own nodes, while sibling letters `6.01(a)`/`6.01(b)` under the *same* parent did. An independent second-pass check (§39-40) using a genuinely separate method (raw-text regex search for the lettered marker at a real clause-start position, bypassing the structural index entirely) confirmed 7 of 8 sampled cases show the real, well-formed clause physically present in the source with no corresponding node — ruling out "the ground-truth reference is simply wrong" as an alternative explanation.

24. **The floor mechanism's own apparent gap turns out to be the same defect wearing a different face.** Of the 13 residual cases classified `R11_MATERIALITY_INHERITANCE_NOT_TRIGGERED` (a closure-admitted unit whose contextual-materiality floor never fired), **12 of 13** have an immediate parent that *itself* suffers the identical duplicate-nodeKey/empty-`OWN`-text corruption — e.g. the Events of Default chapeau (`doc-a::7.01`, duplicate count 4) shows `materiality: INFORMATIONAL`, `detectedSignals: []`, `excerptText: ""` in the DSGR regression's own real output, despite governing an unambiguously operative, materially significant enumerated list. Workstream B's floor logic (`applyContextualMaterialityFloor`) correctly declined to elevate from a parent it could not itself read as operative — the floor is not narrow here; its input is corrupted.

25. **Combined attribution: ~79% of the entire 89-case residual population.** 58 primary (65.2%) + 12 secondary via R11's parent-corruption dependency (+13.5%) = **70 of 89 (78.7%)** trace to this one generalizable, pre-existing Phase 2A defect — see `phase-3f1-1-root-cause-taxonomy.json`'s `r17CombinedPrimaryPlusSecondary` field.

## 41-43: Pareto and the resulting architecture decision

41. **Pareto**: top-1 (R17) = 58/89 = 65.2%; top-2 (+R11) = 71/89 = 79.8%; top-3 (+R10) = 81/89 = 91.0%; top-4 (+R1) = 89/89 = 100%. `phase-3f1-1-pareto.json`. Combining R17's primary and secondary attribution (§25) raises the effective top-1 figure to 78.7%.

42. **Gate-realism analysis (task §31): is `strict dangerous-unflagged = 0` achievable via bounded Phase 3E fixes without degenerating into route-everything/mark-everything-material?** The evidence points to a clear, specific answer, not a general one: **yes for the smaller R1/R10 populations (17 cases, 19%) — those are genuinely local router/materiality gaps a bounded, generalizable fix can plausibly close without inflating false positives (Phase 3F.1's own workstream design, closure-depth-bounded and posture-gated, is direct precedent that this can be done safely).** But **no, not for the dominant R17 population (70 cases, 78.7%) — no amount of router-closure-vocabulary or materiality-floor tuning inside Phase 3E can recover a provision whose own text is unreachable by nodeKey, because both of those layers consume `getNodeText`/`getParent`/`getChildren`, which are exactly the APIs this defect corrupts.** Phase 3E cannot out-tune a broken input.

43. **Architecture escalation test (task §32): met.** This is a Phase 2A shared-substrate defect — the *same* failure category Architecture Invariants #18 named as the one Phase 2F's original remediation did not architecturally eliminate, now demonstrated recurring in a new, generalizable form (§31 above is direct case-level proof it defeats two independently-built systems - discovery and audit - simultaneously, on 75% of their joint-miss population). This is not "residuals span many unrelated local heuristics" (the opposite: one dominant, compositional cause) but it squarely matches the deeper principle those triggers exist to protect: **a shared-substrate defect that Phase 3E-local tuning structurally cannot reach.** **Recommendation: `ARCHITECTURE_CHANGE_PROPOSAL`, scoped narrowly to Phase 2A's structural-index node-identity mechanism (`lib/contract-model/compiler/structural-index.ts`'s `buildStructuralIndex` and, likely, `stage-structure.ts`'s upstream node-key derivation) — not a broad re-architecture, and not a substitute for the smaller, still-valid bounded fixes in §44-49 below.**
