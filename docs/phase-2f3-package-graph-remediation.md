# Phase 2F.3 — Multi-Document Classification & Relationship Robustness Remediation

**Central question:** can Headroom now safely understand what documents exist in a real multi-document debt package, which underlying instruments they belong to, and how those documents relate, without confidently inventing relationships when the evidence is insufficient?

**Answer: yes, demonstrated on the real, original failing package.** All 5 original Phase 2F Phase-2C issues (PC-01 through PC-05) are reconciled by a real, non-mocked rerun of the remediated package-graph pipeline against the real CONMED package. Document C and Document D — both misclassified as base agreements in the original first-blind run — now classify correctly as `AMENDMENT`. Document D's genuine multi-target amendment (to both the Credit Agreement and the Guarantee and Collateral Agreement) is now fully represented as two distinct, resolved edges. Document B's real dual guarantee-and-security function is now represented via a new composite document type and two resolved relationship edges. The false ambiguity that blocked 67 of 84 cross-document reference leads is eliminated — zero leads remain unresolved. And the one case the original report itself flagged as *correctly* unresolved (Document C's real amendment target is genuinely absent from the package) remains honestly non-committal — never fabricated as certain.

## 7-9. Root-cause analysis (traced from real source before any code change)

7. **Root-cause statement for `PC-01`/`PC-02` (primary defect):** *"`classifyPackageDocuments`'s deterministic scanner checks a fixed, ordered list of rule patterns against a document's ENTIRE preamble (first 3000 chars), with no distinction between text describing the document ITSELF and text the document merely uses to name an OTHER agreement it references. Document C's real text opens '...to the Seventh Amended and Restated Credit Agreement, dated as of July 16, 2021' — a reference to its target — and the scanner matched 'Amended and Restated Credit Agreement' from that reference before ever reaching the AMENDMENT rule. Document D was misclassified for the identical reason via a 'Collateral Agreement' mention naming Document B."* Classification: **`DOCUMENT_TYPE_CLASSIFICATION`** (primary), with **`DOCUMENT_TITLE_EXTRACTION`** as a directly contributing factor (no self-vs-reference distinction existed at all).
8. **Root-cause statement for the reference-matching failure exposed while tracing `PC-01`/`PC-02` (a second, independent, non-classification defect found during root-cause tracing, not assumed in advance):** *"`AGREEMENT_REF_RE`'s prefix alternation only recognized 'First Lien/Second Lien/Senior/Subordinated' before an agreement-type label — it could not match the single most common real-world restatement reference, an ordinal-numbered 'Eighth Amended and Restated Credit Agreement', nor a composite 'Guarantee and Collateral Agreement' name, nor real SEC-filing text-extraction line-wrapping ('Restated Credit\\nAgreement')."* Classification: **`REFERENCED_AGREEMENT_DETECTION`**. This is a genuinely separate defect class from `PC-01`/`PC-02`'s classification bug (it affected the reference-MATCHING regex, not the document-TYPE classifier) — found only because fixing classification alone was insufficient to reproduce the real, expected relationship edges against the real text, and repaired in the same task since it directly blocks the very relationships `PC-01`/`PC-02`/`PC-04` require, not as scope creep.
9. **Root-cause statement for `PC-03`:** *"`RELATIONSHIP_TYPE_BY_SOURCE_CLASSIFICATION` mapped exactly ONE relationship function per document type — a composite document with two real functions (guarantee AND security) was architecturally incapable of producing both edges, regardless of how it was classified."* Classification: **`RELATIONSHIP_RESOLUTION`** (a document-type-vs-document-function conflation, task §6's own named architectural risk). `PC-04` is not an independent root cause — it is `PC-01`'s own traced downstream consequence (a false ambiguity, not a separate defect), confirmed against the original report's own explicit tracing (§33: *"the direct, traced consequence of the §30 misclassification"*). Per the task's own "repair only the smallest generalized class necessary" instruction, no other defect classes (`AMENDMENT_NUMBERING`, `PARTY_MATCHING`, `DATE_EXTRACTION`, `AMBIGUITY_HANDLING`, `MODIFICATION_TARGET`) were found to be independently at fault and none were touched beyond what these three root causes required.

## 10-13. The fixes

10. **Self-referential-title-first classification** (`document-classifier.ts`): a new Tier 1 signal recognizes a document's own explicit self-referential defined term — `(this "Amendment")` — a standard, industry-wide financing-document drafting convention (confirmed independently on both Document C and Document D's real text, not a CONMED-specific phrase), checked BEFORE the original broad preamble scan (now Tier 2, unchanged fallback behavior for any document not using this convention — every one of this module's own 26 pre-existing synthetic tests, which use plainer titling, kept passing unmodified). The captured self-term is matched against the SAME rule table used for the broad scan, so "Amendment" → `AMENDMENT`, "Amended and Restated Credit Agreement" → `AMENDED_AND_RESTATED_AGREEMENT`, etc. — never a second, parallel vocabulary.
11. **Composite `GUARANTEE_AND_SECURITY_AGREEMENT` type** (additive Prisma migration + classifier rule, checked before the plain `GUARANTEE`/`SECURITY_AGREEMENT` rules): added only after real evidence (Document B) showed the existing two types could not jointly represent one common, reusable leveraged-finance document concept — not invented speculatively, and not a CONMED-specific title (the rule matches the generalized phrase pattern "guarant(y/ee) and (collateral/security) agreement", not any exact string).
12. **Referenced-agreement-detection broadening** (`relationship-resolution.ts`): `AGREEMENT_REF_RE`'s prefix alternation now recognizes an ordinal-numbered "Amended and Restated" restatement reference (`"Third Amended and Restated Credit Agreement"` etc. — a standard industry convention, not CONMED-specific) and its label alternation now recognizes composite collateral-document names (`"Guarantee and Collateral Agreement"`, `"Pledge and Security Agreement"`, etc.). A `ws()` helper converts every literal space in a multi-word phrase to `\s+` before it reaches the final regex, so real text-extraction line-wrapping (confirmed real: `"Restated Credit\nAgreement"`) no longer silently defeats a match — applied to every phrase in this module, not only the one evidence happened to catch.
13. **Document-type-vs-function separation** (`RELATIONSHIP_TYPES_BY_SOURCE_CLASSIFICATION`, task §6): the map is now array-valued — a document's classification may imply MORE than one real relationship function. `GUARANTEE_AND_SECURITY_AGREEMENT` maps to `["GUARANTEES", "SECURES"]`; every other existing type keeps its single function unchanged. One relationship candidate is generated per (function × reference) pair, so a composite document referencing one target produces two edges, and a multi-target amendment (one function, two references) produces two edges — the existing `RelationshipCandidate` edge architecture is reused unmodified, per the task's own "reuse existing relationship-edge architecture where possible" instruction; no parallel model was built.

## 14-16. Instrument identity, ambiguity, and negative evidence (largely unchanged by design)

14. **Instrument identity model:** unchanged in its core algorithm (union-find over `RESOLVED` `AMENDS`/`RESTATES`/`SUPPLEMENTS`/`JOINS` edges only — never `REVIEW_REQUIRED`/`UNRESOLVED`, so an amendment whose target is merely plausible, not confirmed, never merges instruments). `NON_INSTRUMENT_TYPES` was extended to include the new composite type, so Document B (a cross-cutting guarantee-and-security document) is correctly excluded from instrument grouping and instead associated with Document A's instrument via its own `GUARANTEES`/`SECURES` edges — exactly the architecture the module's own pre-existing header comment already specified for `GUARANTEE`/`SECURITY_AGREEMENT`, now correctly extended to the new type.
15. **Ambiguity model:** unchanged (`RESOLVED`/`REVIEW_REQUIRED`/`UNRESOLVED`, exact type+date match required for `RESOLVED`, type-only match demoted to `REVIEW_REQUIRED`, anything else `UNRESOLVED` with the real candidate hint preserved) — the fixes made this existing, already-correct discipline REACHABLE on the real text, they did not change its rules. Verified directly: required scenario 10 (an ambiguous amendment using the new self-referential convention) still correctly stays `UNRESOLVED`.
16. **Negative evidence:** no separate hand-rolled negative-evidence scoring layer was built. The existing architecture already refuses to resolve on party overlap, title similarity, or shared package membership alone — only an exact type+date match ever produces `RESOLVED` — which structurally satisfies task §15's concern (a weak signal never overrides the need for strong evidence) without new machinery. Verified directly: required scenarios 17/18/22/23/24 (different-type same-date, same-agent different-facility, party-overlap-wrong-type, similar-title-wrong-date, one-strong-among-several-weak) all resolve correctly.
