# Phase 2F.2 — Discovery Schema-Contract Robustness + Primary/Auditor Reconciliation

**Central question:** when Pass B semantic discovery encounters a document whose operative content the closed `DiscoveryRole` enum has no member for, does Headroom now tolerate the model's real vocabulary at the wire boundary and recover deterministically, instead of the enum mismatch crashing the entire document's discovery pass the way it did on the real Document B in Phase 2F?

**Answer: yes, demonstrated on the real, original failing document.** The real Document B (A&R Guarantee and Collateral Agreement) — which crashed Phase 2B's discovery pass completely in the original Phase 2F blind run (0 candidates, `AnthropicError: Failed to parse structured output`) — was rerun for real after this task's fix: **96/96 Pass B section calls succeeded, zero section failures, `documentDiscoveryHealth = DISCOVERY_HEALTHY`**, producing 228 real discovered candidates. Independent auditor reconciliation (Phase 2E's own unmodified comparison code, run again against the new candidates) confirms 95 of the original 107 `MATERIAL_DISCOVERY_MISS` findings (89%) are now discovered, including all 3 that were rated `MATERIAL` severity; the 12 that remain are all `UNCERTAIN` severity.

## 9-11. Root-cause classification

9. **Root-cause statement (written before implementation):** *"The Pass B semantic-discovery wire schema binds the model's free-text characterization of 'what this rule does' directly to a closed 16-member Zod enum with no tolerant boundary layer. When Document B's content (guarantee/security concepts) has no close enum member, the model does not mis-pick the closest wrong token — for most sections it emits a full descriptive sentence instead. The Anthropic SDK performs its own strict client-side Zod validation before application code ever inspects the result, so this mismatch throws inside the SDK itself and propagates through pipeline.ts's un-guarded per-section loop, destroying the entire document's discovery pass."*
10. **Primary classification: `MODEL_OUTPUT_NORMALIZATION_GAP`.** Contributing factors: `CLOSED_ENUM_TOO_NARROW` (no member represents guarantee-obligation/security-grant/waiver/liability-cap/representation concepts) and `BATCH_ATOMICITY` (the per-section loop had zero fault isolation, independent of the enum-narrowness issue — any exception in any section, for any reason, aborted every remaining section).
11. **Explicitly ruled out:** `PROVIDER_STRUCTURED_OUTPUT_MISMATCH` (the model returned well-formed JSON matching every other field correctly — only the semantic content of one string value fell outside the closed vocabulary) and `VALIDATION_POLICY_TOO_STRICT` (the internal canonical type's strictness is correct; the defect is the absent tolerant boundary in front of it, not that the internal type is too strict per se).

## 12-16. Architecture: tolerant boundary → deterministic normalization → canonical type

12. **Wire schema widened** (`pass-b-semantic.ts`): `role: z.enum(DISCOVERY_ROLES)` → `role: z.string()`; `families: z.array(zodEnumFromPrismaEnum(CovenantFamily))` → `families: z.array(z.string())`. This is the SDK-boundary schema passed to `caller.call()` — the model's raw JSON now always parses successfully regardless of vocabulary drift.
13. **Canonicalization layer** (`discovery/normalization.ts`, new): `normalizeDiscoveryRole(raw)` and `normalizeDiscoveryFamily(ies)(raw)`. Never throws; always returns `{ canonical, status, rawValue, reason }` where `status ∈ {VALID_CANONICAL, NORMALIZED_CANONICAL, FALLBACK_REVIEW_REQUIRED, INVALID_UNUSABLE}`. Matching tiers, in order: exact match → case/punctuation/camelCase/singular-plural-normalized exact match → documented alias table → (role only) ordered keyword classifier for descriptive sentences → fallback to `OTHER_RELEVANT_RULE`/dropped, explicit and reviewable, never silently discarded.
14. **5 new `DiscoveryRole` members added**, each justified as a materially distinct, reusable guarantee/security-agreement concept observed independently across multiple real sections (not a CONMED wording variant): `GUARANTEE_OBLIGATION` (grant/duration/reinstatement/non-impairment of a guarantee), `SECURITY_GRANT` (grant/scope of a security interest or lien), `WAIVER` (express waiver of a notice/defense/procedural right), `LIABILITY_CAP` (fraudulent-transfer/insolvency savings cap), `REPRESENTATION` (representation/warranty of fact). No other new roles were added — release mechanics, subrogation limitation, and defined-term-declaration content are deliberately left to normalize onto existing roles (`CONDITION`, `GENERAL_PROHIBITION`, `OTHER_RELEVANT_RULE`) per §12's "prefer normalization/fallback" instruction, since the evidence for a dedicated role in each case was not broader than one wording variant.
15. **`families` handling:** unlike `role`, no keyword classifier — the real evidence base never showed a `families` value that couldn't be resolved by exact/normalized/alias matching (see items 30-32), consistent with `CovenantFamily` already covering this document type adequately.
16. **Provenance preserved end-to-end** (task §7/§9): `roleRaw`/`roleNormalizationStatus`/`familiesRaw`/`familiesNormalizationStatus` threaded through `pass-b-semantic.ts` → `pass-c-neighborhood.ts` (`ExpandedCandidate`) → `pass-d-reconcile.ts` → the final `DiscoveredCandidate`. A `FALLBACK_REVIEW_REQUIRED`/`INVALID_UNUSABLE` role normalization now force-sets `needsReview = true` regardless of what the model itself claimed.

## 17-19. Candidate/batch-level fault isolation

17. **Fault isolation implemented at the section-call level** (`pipeline.ts`): the loop over Pass-A-flagged sections wraps `runPassBSemanticClassification` in a `try/catch`; a failure is recorded as a `DiscoverySectionFailure` (`sectionNodeKey`, `sectionRef`, `stage`, `errorMessage`) and the loop `continue`s — every other section's candidates survive.
18. **Candidate-level isolation is achieved structurally, not via retry:** because normalization never throws, a single malformed item within an otherwise-valid batch can no longer take down its siblings (proven by required test 7 — one deliberately unrecognizable role among two valid ones; all three survive with correct, independent statuses). No large-batch retry logic was added — unnecessary, since the root defect (the SDK-level enum throw) is eliminated at the schema boundary, not papered over with retries.
19. **Document-level discovery health** (`DiscoveryHealthState`, task §18): `DISCOVERY_HEALTHY` (0 attempted or 0 failures) / `DISCOVERY_PARTIAL` (some but not all attempted sections failed) / `DISCOVERY_FAILED` (every attempted section failed). Wired into `package-safety.ts`, additive to the Phase 2F.1 shape (`discoveryHealth`, `discoveryInputInsufficient` on `DocumentSafetyEntry`; `DISCOVERY_FAILED` → `PACKAGE_UNSAFE`, `DISCOVERY_PARTIAL` → `PACKAGE_REVIEW_REQUIRED`) — never modifies Phase 2E's own independent inventory logic (task §19: not touched).

## 54. Known limitations

- 12 of the original 107 Document B auditor findings remain genuinely undiscovered (all `UNCERTAIN` severity, none `MATERIAL`) — disclosed, not hidden (items 36-37).
- The role keyword classifier is heuristic by construction (documented in `normalization.ts`'s own comments) — one deliberately imperfect case was found and accepted during design (a "does not limit... liability" non-impairment clause can match the `LIABILITY_CAP` keyword rule despite negating rather than imposing a cap); this is judged acceptable because normalization status and the model's own `confidence`/`needsReview` remain the authoritative downstream review signals, not the bucket assignment itself (task §9: "normalization is not correctness"). This particular ambiguity was not exercised in the real Document B rerun, since the model returned exact valid enum tokens for `role` in every real call (item 32).
- 4 real out-of-enum family values remain honest, deliberate fallbacks (item 34) — not bugs, but a disclosed limit of how far generalized normalization reasonably extends before it would require either a real ontology decision (`Intellectual Property`) or an under-evidenced guess (`Restrictive Agreements`).
- `DISCOVERY_PIPELINE_VERSION`/`DISCOVERY_PROMPT_VERSION` were both bumped (v1→v2); confirmed via the real rerun that Document B — whose only prior cache state was a crash, never a successful cached result — required a full fresh run, but idempotency of the NEW version against itself (a second identical rerun reusing cache) was not separately re-verified in this task, since Phase 2B's discovery cache wiring into `ContractCompilerStage` remains, as in Phase 2F.1, "available as a library, not yet wired into the live orchestrator."
- Goldens/protected-data/tenant-isolation DB-backed checks could not be executed in this sandbox (items 47-49) — disclosed, not silently skipped, identical condition to every prior phase this session.
