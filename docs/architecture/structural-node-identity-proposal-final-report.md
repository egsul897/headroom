6. **Architecture conflict identified:** `nodeKey` (`stage-structure.ts:244`, `${documentId}::${normalizedSectionRef}`) is constructed and treated as a unique per-occurrence identity, but is actually a human drafting **label**, which is not unique — the same label can be produced by more than one physical source location (cross-reference sentences, ToC entries, malformed duplicate numbering, amendment-quoted text).
7. **Current nodeKey construction:** `nodeKey: \`${doc.documentId}::${r.sectionRef.replace(/\s+/g, "")}\`` (`stage-structure.ts:244`). `sectionRef` comes from whichever of `ARTICLE_PATTERNS`/`SECTION_PATTERNS`/`INTEGER_SECTION_PATTERNS`/`BARE_INTEGER_SECTION_PATTERN`/`clause-hierarchy.ts` matched. `ordinal` (sibling position, already computed at `stage-structure.ts:219-225`) is discarded before identity is formed.
8. **Current collision mechanism:** `buildStructuralIndex` (`structural-index.ts:72-89`): `byKey.set(n.nodeKey, n)` iterated in `charStart` order — last-charStart occurrence silently overwrites any earlier one sharing the label (ordinary `Map.set` semantics on a never-actually-unique key); `childrenByParentKey` merges every node whose `parentSectionRef` label matches, across colliding parent occurrences, with no ownership check. `allNodes()` still returns every physical occurrence — only the identity-keyed maps lose information, which is why the defect is "unreachable," not "missing."
9. **Minimal synthetic reproduction:** `scripts/architecture-proposal-node-identity-repro.ts` — imports and calls the real, unmodified `parseDocumentStructure`/`buildStructuralIndex` against a synthetic (non-DSGR) document. Case A: a cross-reference sentence satisfying the SECTION heading regex produces a second physical `"6.04"` node; `getNodeByRef` resolves only to the later occurrence (`charStart=252`); the earlier one (`charStart=117`) becomes permanently unreachable by identity lookup though it still exists in `allNodes()` (9/9 nodes present). Case B forces both occurrences to carry lettered children, making the cross-parent merge directly observable: `getChildren("synthetic-doc-b::6.06")` returns 3 children mixing both physical occurrences' children, and produces a **second-level** collision (`"6.06(a)"` appears twice), proving the defect recurses at every nesting depth. Preserved output: `tests/fixtures/architecture-audits/structural-identity-collision-repro.json`; re-verified reproducible by `tests/contract-model/architecture-proposal-node-identity.test.ts`.

11. **Responsibilities currently overloaded into nodeKey:** map key (`byKey`/`childrenByParentKey`/persistence upsert), human-readable label, "the provision" routing/reconciliation/reference-resolution treat as ground truth, an assumed-but-unverified stable identity, and a partial input to IR rule identity (`computeRuleId`). See ADR §3.
12. **Source-occurrence identity requirements:** unique within a document; deterministic across identical (source bytes + parser version) reruns; independent of traversal/array-insertion order; resistant to duplicate human labels; instrument-scoped; cheap; serializable; usable as a map key; no DB-autoincrement dependence; no model-generated component. See ADR §5.
13. **Legal-reference identity requirements:** `sectionRef` remains the citation text, used purely as a lookup/query key (`findByLegalRef`/`resolveCitation`), returning zero, one, or many `StructuralNode`s explicitly — never silently disambiguated by collision, never treated as identity. See ADR §9.
14. **Structural-path requirements:** derived, non-identity display/debug field (sequence of ancestor `nodeId`s), computed top-down only after `nodeId`s already exist — never itself consulted for equality or lookup, and not assumed universally unique (duplicate full paths are possible and handled the same way duplicate labels are: informational, not identity-bearing). See ADR §8/§9.
15. **Amendment-lineage requirements:** explicitly a separate mechanism (Phase 2G's own amendment-effect/operative-state machinery); a `nodeId` never doubles as cross-version/cross-amendment identity, and vice versa; an amendment quoting an existing section produces a **new**, distinct `nodeId` for the quoted occurrence — correct, since occurrence identity answers "what physical text is this," not "which logical provision does this represent over time." See ADR §11.
16. **Option A:** span-primary (`computeStableKey("structural-node", documentId, nodeType, String(charStart))`). Deterministic, near-collision-proof by construction, cheap, reuses the existing `computeStableKey` repo convention, Level-A stability only (intentional). See ADR §5/option-comparison artifact.
17. **Option B:** ancestry path + occurrence ordinal. Rejected as primary — circular bootstrapping (a node's id depends on its parent's, all the way to the root, but "which physical node is the parent" is exactly the disputed question) and fragile to reordering. Retained only as derived display metadata under the selected option.
18. **Option C:** content-derived hash + source position. Rejected — introduces **new** collisions from verbatim-repeated boilerplate across genuinely distinct provisions, and has a circular dependency on the very defect being fixed (a node's "own text" is only correctly known once children are occurrence-safely attributed).
19. **Option comparison:** full criteria matrix (determinism/uniqueness/collision risk/stability/readability/performance/migration complexity/parser- and extraction-version sensitivity/amendment behavior/downstream ergonomics) for all 5 options (A-E) recorded in `tests/fixtures/architecture-audits/structural-identity-option-comparison.json`. Option E is corroborating prior art (Prisma `DocumentNode.parentId`, a real FK), not a candidate construction.
20. **Preferred design: Option D** — hybrid: Option A's `nodeId` construction as the actual identity, plus `structuralPath`/`occurrenceOrdinal` (Option B's useful fields) carried as strictly-additive, non-identity display metadata. Selected because it is simultaneously collision-proof against the exact drafting patterns that caused the DSGR residuals, cheap/non-circular, consistent with the existing repo hashing convention, and does not sacrifice debuggability.
21. **Preferred ID construction:** `nodeId = computeStableKey("structural-node", documentId, nodeType, String(charStart))` — reuses `lib/contract-model/stable-keys.ts`'s existing sha256-hex-slice convention verbatim; no new hashing scheme.
22. **Determinism semantics:** same source bytes + same parser version ⇒ same `charStart`s ⇒ same `nodeId`s (verified: `parseDocumentStructure` is a pure function, no Map-iteration-order dependency reaches `charStart`). Four required verification forms specified (repeated-run, shuffled-input-order, serialize/round-trip, process-restart) in `structural-identity-validation-plan.json`.
23. **Parser-version semantics:** `nodeId` is deliberately **not** guaranteed stable across a parser algorithm version change — a parser change should mint new identities, not silently keep stale ones, per ADR §6.
24. **Extraction-version semantics:** deliberately **not** guaranteed stable across a re-extraction (PDF vs HTML, redline handling) — a different source representation should mint different identities, per ADR §6/§14.
25. **Collision behavior:** collision is believed near-impossible by construction, but never assumed away — any detected `nodeId` collision at build time must produce a hard-fail `DUPLICATE_OCCURRENCE_ID` health finding and downgrade that document's structural trust, never a silent last-write-wins pick. This closes the exact silent-overwrite failure mode this proposal exists to eliminate.
26. **Document scoping:** `nodeId`'s hash input always begins with `documentId` — cross-instrument collision is impossible **by construction**, not merely by convention, preserving today's one correctly-working property of the label scheme (I14).
27. **Parent-child model:** `parentId`/`childrenByParentId` keyed by occurrence `nodeId`, never by a re-normalized `parentSectionRef` label string — I4/I6.
28. **Proposed index API:** `nodesById` (1:1), `childrenByParentId`/`parentByChildId` (occurrence-safe), `nodesByLegalRef`/`nodesByDisplayLabel` (many-valued multi-maps), `nodesBySourceSpan` (interval-indexed), `roots()`, `orphans()`, `ambiguities()`, `healthDiagnostics()`. See ADR §13.
29. **Singleton-vs-multi lookup policy:** exactly three API shapes permitted — `getByOccurrenceId` (1 or hard-fail), `findByLabel/findByLegalRef/resolveCitation` (0-to-many, explicit `AmbiguityReport`), `getChildren(parentNodeId)` (ordered, occurrence-owned). No other shape (today's raw-string-keyed `getChildren(nodeKey)` included) is permitted to survive into the new API. See ADR §14.
30. **Source-span model:** `{documentId, charStart, charEnd}`, formalized as part of `nodeId`'s own construction input (via `charStart`) — one span per `nodeId`.
31. **Own-text/subtree-text model:** `getNodeText(nodeId, "OWN")`'s existing boundary computation (`structural-index.ts:189-198`) is already correct in principle; the defect is purely that `getChildren` can return wrong-occurrence children today. Fixing child ownership (I6) fixes this boundary computation for free, with no separate remediation required. See ADR §15.
32. **Structural invariants:** I1-I16 fully enumerated with enforcement mechanism for each, `tests/fixtures/architecture-audits/structural-identity-proposed-invariants.json`; critical discipline flagged explicitly: `DUPLICATE_LABEL_EXPECTED` (I2) must never be conflated with `DUPLICATE_OCCURRENCE_ID` (I1/I5) — only identity-level invariants are hard failures.
33. **Health diagnostics:** `DUPLICATE_OCCURRENCE_ID`, `IMPOSSIBLE_PARENT`, `MULTIPLE_STRUCTURAL_PARENTS`, `ORPHANED_NODE`, `CYCLE`, `INVALID_SOURCE_SPAN`, `OVERLAPPING_INCOMPATIBLE_SPAN`, `AMBIGUOUS_LEGAL_REFERENCE` (informational), `DUPLICATE_LABEL_EXPECTED` (informational, never a failure), `DUPLICATE_NORMALIZED_PATH` (informational), `SOURCE_ORDER_VIOLATION`. See ADR §17.
34. **Source reachability:** a mechanical, purely span-arithmetic coverage/gap invariant — every document byte is either inside some node's own span or explicitly accounted for as inter-node text, with no unexplained gap. Computable today on the corrected index with zero LLM/semantic involvement; gives Phase 2B/3E a cheap, shared, structural-only early-warning signal. See ADR §18.
35. **Raw-source fallback:** Phase 2F.1's existing fallback logic (`structural-coverage.ts`) must be audited by the future implementation to confirm it does not itself resolve gaps via the same collision-prone lookups — flagged as an open verification item, not resolved in this proposal (requires reading that module in full, out of this pass's scope). See ADR §20.
36. **Shared-substrate safety:** addressed via the reachability invariant (item 34) plus raw-source fallback independence (item 35) — not via a second parser. Gives Phase 2B and 3E a real, cheap, structural-layer-only signal that a structural read is untrustworthy, directly responsive to Architecture Invariant #18, without doubling the parsing surface.
37. **Second-parser recommendation: No.** Explicitly evaluated and rejected — cost, new-bug risk, and an unsolved disagreement-resolution problem outweigh the marginal independence gain over the cheaper mechanical reachability-invariant approach. **Recommendation: a robust primary parser + independent mechanical source-coverage checks.** See ADR §19.
38. **Raw-source root-of-trust recommendation:** the layered model (raw/extracted text is root of trust; structural index is a derived representation; semantic inventory is a further derived representation, each retaining enough provenance to verify against the prior layer) is recommended as an explicit architecture principle for a future implementation phase to formalize — not adopted as a new invariant in this proposal itself (this proposal does not edit `docs/HEADROOM-ARCHITECTURE-INVARIANTS.md`). See ADR §47-equivalent discussion (folded into §18/§20 of the ADR).

The module's own doc-comment explicitly, deliberately reuses "one real identity scheme, not two" — a considered design choice that turned out to be wrong, not an oversight.
50. **Prisma impact:** **no schema migration required.** `DocumentNode.parentId` is already a real FK (correct shape, positive prior art). Only the `stableKey` **formula** in `persistence.ts` needs the disambiguating input (mirroring `nodeId`'s construction) — no new column, no new model.
51. **Cache impact:** any cache keyed off today's `nodeKey` (directly or via a hash incorporating it, e.g. `structureOutputHash` — which, notably, already includes `charStart`, making it more correct than the identity scheme it caches output of) is invalidated by an identity-scheme change. Proposed mechanism: a `STRUCTURAL_INDEX_VERSION` constant participating in every derived cache/artifact key, bumped once at implementation time.
52. **Provenance impact:** today's provenance conflates citation and occurrence via `nodeKey`. Migrating provenance to carry `nodeId` alongside the unchanged `sectionRef` lets a reviewer trace a rule to the exact physical text (span/excerpt), not merely to a possibly-ambiguous citation.
